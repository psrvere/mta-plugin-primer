Writing an MTA plugin

How we turned a BuildConfig migration tool into a crane plugin, for someone about to do the same with Jenkins2Tekton.

Goal

After reading this you know what an MTA crane plugin is, how ours is built, and which questions a Jenkins2Tekton plugin ADR has to answer.

In short

crane moves an application from one Kubernetes cluster to another in three steps: export, transform, apply. A transform plugin is a small program that crane runs once for each exported resource. It reads one resource as JSON and returns what to change.

Our plugin turns an OpenShift BuildConfig into a Shipwright Build. It never calls a cluster. One bad resource never stops the run. What it could not convert is listed in an annotation on the output and in the log.

The first question for a Jenkins2Tekton plugin is what it reads. A crane plugin only sees resources exported from a cluster. A Jenkinsfile in a Git repository is not one of them.

A JenkinsPipeline BuildConfig holds the Jenkinsfile inline in jenkinsfile, or names its path in the Git source with jenkinsfilePath. In the second case the plugin gets the path, not the file.

1. MTA and crane

crane is the Konveyor tool for moving workloads between clusters.1 MTA builds its own crane binary, named mta-ops, from the migtools/mta-crane repository.2 The commands are the same, so this page says crane for both.

Each step writes files to disk, so you can read the result before anything reaches the target cluster.

2. What a transform plugin is

A plugin is a separate binary. crane starts it once per resource, writes one JSON object to its standard input, reads one JSON object back, and the process exits. Two hundred BuildConfigs means two hundred runs.4

The plugin can answer in one of three ways:

  • Not my resource. Return nothing, and crane passes it through.
  • Converted. Delete the original and add new resources.
  • Not converted. Add a JSON patch, in our case two annotations saying why.

A plugin sees one resource and a flat map of flags. It never sees the other resources in the export.5 Users pass the flags with --optional-flags.

A plugin error stops the whole crane run.4 That shapes most of the design in section 4.

There are two ways to ship a plugin. Upstream crane installs it from a plugin index with crane plugin-manager add.6 The MTA build compiles ours in, off by default, so it runs only when the user names it in crane transform.3 A plugin from the index is any executable that speaks the JSON protocol. A compiled-in plugin is a Go package, so its Go version and dependencies must agree with mta-crane's.7

One crane transform can run several plugins. Each named plugin becomes a stage, in the order given on the command line, and each stage reads the previous stage's output.8 If your plugin and ours run together, decide which goes first.

3. What our plugin does

It reads a BuildConfig (build.openshift.io/v1) and writes a Shipwright Build (shipwright.io/v1beta1), the resource Builds for Red Hat OpenShift runs.3 It replaced the crane convert command from the January developer preview. That command called the source cluster to resolve image references.95

JenkinsPipeline BuildConfigs pass through with two annotations saying they were skipped. A Jenkins2Tekton plugin could pick those up.3

Every BuildConfig ends in one of four states.10

StateMeaningWhere it is recorded
convertedA Build was made and nothing was droppedAnnotation on the new Build
converted-with-warningsA Build was made, but some fields were dropped or need a personSame, plus the warning text
skippedThe plugin chose not to convertTwo annotations on the original
failedConversion hit an errorTwo annotations on the original

Each warning has a numbered entry in the support matrix. The entry says what was lost and what to do by hand.11

4. Decisions worth copying

We record each decision the code must keep obeying as an ADR in docs/adr/.12 These six carry over to any migration plugin.

ADRDecisionWhy
0001Work offline. Never call a cluster.Users convert exports from clusters they no longer have. Anything that needs cluster data becomes a flag or a warning.
0002Four outcomes. Never return an error for one bad resource.crane stops the whole migration on a plugin error. Only the plugin knows the failure is local.
0008Keep what you cannot convert, in an annotation, and warn.A trigger written to a target that ignores it looks set up and does nothing. A copy in an annotation lets a person rebuild it later.
0006Never overwrite what crane already migrates. Never guess a name.A generated ServiceAccount with the same name as the real one would replace it on apply. A guessed secret name gives a Build the cluster rejects.
0010Target the product's catalog, and say which one.Upstream Shipwright has no buildah strategy. A Build that names it never registers there.
0004Treat parameter names on the target as a contract, tested on a cluster.A wrong parameter name passes every offline test and fails on the cluster.

The design started from Konveyor enhancement PR 300.13 Each ADR says where it follows that proposal and where it departs.

5. How we ran the work

  1. Enhancement proposal. Agree the scope upstream in konveyor/enhancements before writing code.13
  2. Field map. List every source field and decide for each one whether it converts, warns or drops. Ours became the support matrix.11
  3. Plugin repository. One repo with the code, an architecture page, ADRs and worked examples. A test regenerates the examples on every CI run and fails when the output drifts.14
  4. Cluster test per feature. Unit tests are not enough. For each feature we ran export, transform and apply, then ran the build on a real cluster.
  5. Release. Add the plugin to the crane plugin index and write a known limitations page.15

6. Questions for your ADR

QuestionWhat we chose, for comparison
What does the plugin read? JenkinsPipeline BuildConfigs in a crane export, Jenkinsfiles in Git, or a Jenkins server?BuildConfigs from the export. Only the first option fits a crane plugin as it works today.
What does it write? Pipeline, PipelineRun, Tasks, triggers?A Build, plus a ServiceAccount or ConfigMap when needed. Never a run, because a run in the output would start on apply.
Which target catalog? Which Tasks will exist on the cluster?The Builds for Red Hat OpenShift strategy catalog, named in ADR 0010.
What happens to a step that does not convert?Warn on the output, keep the original in an annotation.
How does a reader find what did not convert?An outcome annotation on every resource, and the warning text in crane.konveyor.io/conversion-warnings on the output. One grep over the output directory finds them all.
Can it work offline?Yes, and it must. Flags replace cluster lookups.
How do credentials move?crane moves the Secrets. The plugin points at them by name and never invents one.
How does it ship? Plugin index, compiled into MTA, or both?Both. Index for upstream crane, built in for MTA.
